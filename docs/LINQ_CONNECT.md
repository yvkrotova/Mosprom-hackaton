# Подключение проверенной YOLOv8s TPU к проекту

Подготовлено 24 октября 2026. Код адаптера проверен локальными тестами. Сквозной запуск
этой сборки сайта на машине команды ещё не выполнен: нужен доступ к RabbitMQ и пакет
организаторов. Сама TPU-программа ранее успешно запускалась в Jupyter на фото и видео.

## Что изменено

- `backend/app/pipeline/detectors/linq.py`: вместо заглушки — реальный транспорт.
- `backend/app/pipeline/detectors/linq_transport.py`: протокол из example.ipynb организаторов.
- `backend/app/config.py`: LINQ_TIMEOUT_S.
- `backend/requirements-linq.txt`: дополнительная зависимость pika.
- `backend/tools/check_linq_connection.py`: проверка импортов, TCP и настоящего кадра.
- Тесты транспорта и обновление ожиданий прежней заглушки в test_pipeline.py и test_worker.py.

Фронтенд, БД, трекер, правила бега, опасной зоны и blocked_exit не изменены.
Не заменяйте ваш .env файлом .env.example. Архив не содержит ваших весов, видео,
локальной БД, .env, .venv. Они должны остаться в существующем проекте.

## 1. Установка файлов

Остановите backend. Сделайте резервную копию актуального проекта.
Распакуйте архив обновления и скопируйте содержимое его папки `Mosprom-hackaton-frontback`
поверх соответствующей папки проекта, подтвердив замену перечисленных файлов.
Не удаляйте существующие каталоги целиком. Для контроля перечень — PATCH_FILES.txt.

## 2. Библиотеки и сеть на машине с backend

Из PowerShell, находясь в `backend`:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements-linq.txt
.\.venv\Scripts\python.exe -c "import pika; import tpu_pycloud_format; print('OK')"
Test-NetConnection <адрес-RabbitMQ-LinQ> -Port 5672
```

Если нет tpu_pycloud_format, получите клиентский пакет (wheel) из материалов
организаторов Python API и установите его с зависимостями именно в backend/.venv:

```powershell
.\.venv\Scripts\python.exe -m pip install "C:\путь\к\полученному_пакету.whl"
```

Путь выше — шаблон: используйте настоящее имя wheel. Не устанавливайте случайный
одноимённый пакет из интернета. tpu_framework — компилятор, для этого клиента не нужен.
Нельзя просто переносить Linux-окружение из Jupyter на Windows.

Если wheel нет, запустите в терминале Jupyter следующую команду и передайте её вывод
для определения точной версии и расположения клиентского пакета (без импорта SDK):

```bash
/opt/conda/bin/python - <<'PY'
from importlib import metadata
names = metadata.packages_distributions().get('tpu_pycloud_format', [])
for name in names:
    d = metadata.distribution(name)
    print('Distribution:', d.metadata['Name'])
    print('Version:', d.version)
    print('Requires:', d.requires)
    print('Location:', d.locate_file(''))
if not names:
    print('Нет метаданных: нужен клиентский пакет из материалов организаторов.')
PY
```

TcpTestSucceeded должен быть True. Если False — включите VPN организаторов на этой
машине. Открывающийся Jupyter ещё не доказывает доступность брокера напрямую.
Если маршрута всё равно нет, уточните доступ у организаторов или запускайте backend
в разрешённой сети. Не открывайте брокер в публичный интернет.

## 3. Настройки .env

Сначала оставьте DETECTOR=onnx для обычной работы сайта. Обновите только ключи ниже
в существующем backend/.env; не оставляйте дубликаты одинаковых ключей:

```dotenv
LINQ_API_URL=amqp://<адрес-RabbitMQ-LinQ>:5672/
LINQ_LOGIN=<логин RabbitMQ>
LINQ_PASSWORD=<пароль RabbitMQ>
LINQ_PROGRAM=/auto/cache/<пользователь>/<программа>.tpu
LINQ_TIMEOUT_S=60
MODEL_INPUT_SIZE=640
```

Логин и пароль RabbitMQ — из материалов организаторов (это не пароль Jupyter); в репозиторий их не кладите.
LINQ_PROGRAM — серверная копия, созданная проверочным скриптом при сравнении видео.
Она отличается от исходного пути в /home/... . Windows не должен читать этот файл:
путь передаётся воркеру LinQ в file://...?... .

Если серверная копия потеряна, в Jupyter выполните:

```bash
cp ~/work/linq_yolov8s/<каталог компиляции>/<программа>.tpu /auto/cache/<пользователь>/<программа>.tpu
```

## 4. Проверка перед включением на сайте

Сохраните test2.jfif на компьютере. Из backend:

```powershell
.\.venv\Scripts\python.exe -m tools.check_linq_connection
.\.venv\Scripts\python.exe -m tools.check_linq_connection --image "C:\путь\к\test2.jfif"
```

Первая команда проверяет импорты и TCP, вторая — реальную авторизацию, TPU и
декодирование. Она всегда вызывает LinQ, даже если DETECTOR пока onnx.
При ошибке сохраняется исключение: ошибки не превращаются в «людей нет».
Не переключайте сайт до успешной проверки.

## 5. Включение LinQ и запуск

В существующем backend/.env измените DETECTOR на linq:

```dotenv
DETECTOR=linq
```

Остальные настройки сценариев и трекера оставьте прежними. Перезапустите backend:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8000
```

Откройте http://localhost:8000 . Начните с одного короткого видео и одного источника.
Задайте опасную зону, проверьте треки, появление событий, журнал и детектор linq_tpu.
Для бега используйте ролик, на котором сценарий уже проверялся. blocked_exit остаётся
CPU-анализом сцены; TPU выполняет детекцию людей, а не все вычисления приложения.

Таймаут LinQ завершает запрос ошибкой; при длительном запросе мониторинг также может
показать отсутствие heartbeat. Это не отсутствие нарушений. После устранения причины
перезапустите источник. Не увеличивайте таймауты без проверки связи.

## Отличия от диагностических картинок

В проекте сохранён общий OpenCV letterbox. В ручном тесте использовался PIL resize:
интерполяция отличается и может слегка менять рамки, поэтому нужен тест именно адаптера.
Сохранены ваши пороги из .env. На сравнениях был порог 0.25; для ByteTrack проект
по умолчанию использует 0.1. Не копируйте порог 0.25 автоматически: слабые детекции
нужны трекеру, фильтрация событий выполняется отдельно.

В raw=False отправляется float32 [1,3,640,640], RGB /255. Сервер сам применяет квантование.
Выход output0 проверяется как float32 [1,84,8400]. Никакой ручной повторной INT8-конверсии.
Соединение и уникальная очередь ответов — на экземпляр детектора; при ошибке соединение
закрывается. Подтверждённая публикация проверяет маршрутизацию, ответа ждём по ID.

inference_ms в существующем контракте включает запрос и ожидание ответа;
время чипа доступно отдельно как detector._session.device_ms и в check_linq_connection.
Фронтенд не получает новое поле device_ms: контракт API не менялся.

потребуется в MODEL_PATH. Автоматического fallback на CPU в адаптере нет.
