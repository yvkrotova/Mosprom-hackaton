# Эксперимент: базовый детектор YOLOv8s (COCO) на видео цеха

Кейс LinQ — контроль нарушений промышленной безопасности по видео. Цель эксперимента — понять, что «из коробки» даёт
предобученный YOLOv8s (80 классов COCO) с трекингом ByteTrack как **детектор людей**, сколько он стоит по времени
на CPU и готов ли ONNX-экспорт для переноса на ускоритель LinQ.

## Команды запуска (Windows, PowerShell, из корня репозитория)

```powershell
python -m venv .venv
.\.venv\Scripts\activate
python -m pip install -r requirements-experiment.txt

# веса и видео в git не хранятся — положить вручную:
#   models\yolov8s.pt, data\videos\0_te1.mp4

# 1. детекция + трекинг + бенчмарк для камеры из конфига (classes/conf/imgsz берутся из configs\cameras.yaml)
python scripts\run_yolo_video.py --camera cam_01

#    то же с явными параметрами (аргументы командной строки переопределяют конфиг)
python scripts\run_yolo_video.py --camera cam_01 --classes 0 --conf 0.35

#    быстрый прогон на первых 300 кадрах, другие классы
python scripts\run_yolo_video.py --camera cam_01 --classes 0,2,7 --conf 0.25 --max-frames 300

#    без конфига — произвольное видео
python scripts\run_yolo_video.py --source data\videos\0_te1.mp4 --classes 0

# 2. экспорт в ONNX (opset 12, 640x640, static, onnxslim)
python -c "from ultralytics import YOLO; YOLO('models/yolov8s.pt').export(format='onnx', opset=12, imgsz=640, dynamic=False, simplify=True)"

# 3. сверка ONNX (чистый onnxruntime) с PyTorch на 10 кадрах, только person
python scripts\check_onnx.py --onnx models\yolov8s.onnx --pt models\yolov8s.pt `
    --source data\videos\0_te1.mp4 --classes 0 --conf 0.35 --out outputs\cam_01_onnx_check.json
```

Аргументы `run_yolo_video.py`: `--config` (по умолчанию `configs\cameras.yaml`), `--camera`, `--model`, `--source`,
`--classes` (id через запятую), `--conf`, `--imgsz`, `--device` (`auto` → CUDA, если доступна, иначе CPU),
`--max-frames`, `--tracker`, `--out` (по умолчанию `outputs`). Без `--camera` и `--source` берётся первая камера
из конфига.

Артефакты (не в git, `outputs\`):

| Файл | Содержимое |
|---|---|
| `cam_01_annotated.mp4` | видео с боксами, классом, conf и `track_id` |
| `cam_01_detections.csv` | `frame, timestamp_sec, track_id, class_id, class_name, conf, x1, y1, x2, y2` (пиксели исходного кадра) |
| `cam_01_benchmark.json` | среднее pre/inference/post на кадр, FPS, общее время, устройство, параметры прогона |
| `cam_01_onnx_check.json` | покадровая сверка ONNX vs PyTorch |

## Конфиг камер `configs/cameras.yaml`

```yaml
defaults:               # общие значения для всех камер
  model: models/yolov8s.pt
  classes: [0]          # id классов COCO; 0 = person
  conf: 0.35
  imgsz: 640
  device: auto
  tracker: bytetrack.yaml

cameras:
  - camera_id: cam_01                # имя камеры = префикс файлов в outputs/
    source: data/videos/0_te1.mp4    # файл или rtsp://user:pass@host:554/stream
    zone: press_shop                 # название участка
    classes: [0]
    conf: 0.35
    imgsz: 640
```

Приоритет: встроенные значения скрипта < `defaults` < запись камеры < аргументы командной строки.
Любой параметр из `defaults` (в т.ч. `model`, `device`) можно переопределить у конкретной камеры.

## Бенчмарк (PyTorch, CPU, imgsz=640, ByteTrack)

| Метрика | **cam_01: classes=[0], conf=0.35** | для сравнения: все классы, conf=0.25 |
|---|---|---|
| Кадров обработано | 372 / 372 | 372 / 372 |
| Preprocess, мс/кадр | 1.98 | 2.13 |
| Inference, мс/кадр | 82.25 | 97.52 |
| Postprocess, мс/кадр | 1.01 | 1.05 |
| FPS модели (pre+inf+post) | 11.73 | 9.93 |
| FPS end-to-end (декод + трекинг + отрисовка + запись) | 8.15 | 7.13 |
| Общее время | 45.7 с | 52.2 с |
| Устройство | CPU i5-12450H, 8 потоков | то же |

Фильтр классов на скорость самой сети не влияет (это фильтр после NMS); разница в inference ~15 мс — разброс
загрузки CPU между прогонами. Видео идёт с 24.8 fps: на этом CPU реального времени нет (~3× медленнее).
Для real-time нужен ускоритель, прореживание кадров (5–8 fps для контроля людей в зонах достаточно)
или меньший imgsz.

в основном это слабые, но **реальные** люди, а не ложные срабатывания.

## Наблюдения о качестве

**Пропуски.**
- Рабочий у пресса в левой части цеха (виден на кадрах ~120–250) не детектируется вовсе ни при 0.25, ни при 0.35.
- Сидящий человек у левого края кадра и люди, частично закрытые станками, теряются (при conf 0.25 их часть
  уходила в `suitcase`).
- При conf=0.35 в среднем на 1.3 человека в кадре меньше, чем при 0.25: слабые детекции (0.25–0.35) — это
  в основном мелкие/закрытые люди. Для кейса «человек в опасной зоне» пропуск хуже ложной тревоги, так что
  порог 0.35 для этой камеры скорее завышен; подбирать надо по размеченным кадрам.

**Ложные срабатывания.** С `classes=[0]` явных ложных person на просмотренных кадрах нет. Основная проблема —
не ложные, а пропущенные люди.

**Дрожание боксов.** Небольшое: центр бокса смещается в медиане на ~1 px за кадр, высота меняется на ~1 %;
выбросы (p95 ~3 px / ~4 %) — на людях, проходящих за оборудованием, и в дальнем коридоре справа, где группы из
2–3 человек дают слипшиеся боксы и налезающие подписи.

**Стабильность track_id.**
- Два человека в проходе справа (id 1 и 4) ведутся весь ролик без смены id.
- Остальные треки рвутся: 17 id при реальных ~6–8 людях. Короткие треки по 1–20 кадров на людях за станками.
- Повышение conf до 0.35 трекингу **не помогло**: ByteTrack использует низкоуверенные детекции (0.1–0.5) для второго
  этапа ассоциации, а ultralytics отбрасывает всё ниже `conf` до трекера. Например, трек id 5 при 0.25 имел
  25 пропущенных кадров из 234, при 0.35 — 146 из 225.
- Вывод: для трекинга лучше низкий `conf` детектора (0.1–0.25) + фильтр по conf уже при выдаче событий, плюс
  настройка `track_buffer` / `match_thresh` или BoT-SORT с ReID.

**Мелкие объекты.** imgsz=640 на 1080p — уменьшение в 3 раза, люди ~35–80 px по высоте на входе сети. Каски,
жилеты, перчатки на таких людях не различить. Варианты: imgsz 960–1280, тайлинг (SAHI), или двухстадийная
схема «person → кроп → классификатор СИЗ».

## ONNX-экспорт и сверка с PyTorch

- `models/yolov8s.onnx`: opset 12, вход `images [1, 3, 640, 640]` (static), выход `[1, 84, 8400]`, 42.8 МБ,
  упрощён onnxslim 0.1.98, `onnx.checker` проходит.
- Выход — сырая голова без NMS: letterbox и NMS надо реализовать на стороне ускорителя/хоста
  (референс — `scripts/check_onnx.py`, функции `preprocess` / `postprocess`).
- Сверка на 10 кадрах (0, 40, …, 360), только person, conf=0.35, IoU NMS 0.7:

| Проверка | Результат |
|---|---|
| Макс. \|Δ\| сырого выхода ONNX vs PyTorch на одном тензоре | 0.0021 |
| Людей PyTorch / ONNX | 33 / 33 (совпадает на каждом из 10 кадров) |
| Сопоставлено (IoU ≥ 0.5) | 33 из 33 |
| Средний IoU сопоставленных боксов | 0.997 (по кадрам 0.994–0.999) |
| Средняя \|Δconf\| | 0.004 |
| onnxruntime CPU, inference | ~94 мс/кадр |

ONNX эквивалентен PyTorch-модели. Мелкие отличия боксов — из-за разного letterbox: ultralytics для `.pt`
использует прямоугольный вход 640×384, статическая ONNX — квадрат 640×640.

## Покрытие сценариев кейса

| Сценарий | Покрывается YOLOv8s COCO? |
|---|---|
| Наличие/подсчёт людей в кадре | Частично — работает, но с пропусками у оборудования |
| Вход человека в опасную зону (полигон у пресса, проход) | Частично — геометрия поверх bbox person + track_id; качество ограничено пропусками |
| Нахождение в зоне дольше N секунд / одиночная работа | Частично — нужна стабилизация трекинга |
| Отсутствие каски / жилета / спецодежды | **Нет** — классов нет в COCO |
| Перчатки, очки, СИЗ органов дыхания | **Нет** |
| Падение / лежащий человек | Нет напрямую (эвристика по соотношению сторон bbox или pose-модель) |
| Курение, телефон в цеху | Нет / ненадёжно (`cell phone` есть в COCO, но объект слишком мелкий) |
| Погрузчик / техника рядом с людьми | Нет — класса «forklift» в COCO нет |
| Дым, огонь, разлив | **Нет** |
| Перекрытие проходов / эвакуационных выходов | Нет |

## Выводы и следующие шаги

1. YOLOv8s COCO с `classes=[0]` годится как **детектор людей** и база для зональной логики, но не для СИЗ.
2. Порог: conf=0.35 убирает слабые, но реальные детекции и ухудшает трекинг. Предложение — детектор и трекер на
   conf 0.15–0.25, а порог для событий задавать отдельно; подобрать по разметке кадров с камер.
3. Дообучение на датасете СИЗ: person, helmet/no_helmet, vest/no_vest (+ forklift, fire/smoke при необходимости).
   Публичные датасеты: SHWD, Hard Hat Workers, SH17, Construction-PPE; плюс разметка кадров заказчика.
4. Для мелких объектов: imgsz 960/1280 или тайлинг; сравнить по скорости на ускорителе LinQ.
5. Трекер: подобрать ByteTrack (`track_buffer`, `match_thresh`) или BoT-SORT+ReID, чтобы id не рвались.
6. ONNX (opset 12, static 640) проверен и готов к переносу; на ускорителе нужны letterbox и NMS.
