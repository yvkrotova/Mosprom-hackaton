# Эксперимент: базовый детектор YOLOv8s (COCO) на видео цеха

Кейс LinQ — контроль нарушений промышленной безопасности по видео. Цель эксперимента — понять, что «из коробки» даёт
предобученный YOLOv8s (80 классов COCO) с трекингом ByteTrack, сколько он стоит по времени на CPU и готов ли
ONNX-экспорт для переноса на ускоритель LinQ.

## Окружение

| | |
|---|---|
| ОС | Windows 11 Pro 10.0.26200 |
| CPU | 12th Gen Intel Core i5-12450H (GPU с CUDA/MPS нет, только Intel UHD) → `device=cpu` |
| Python | 3.11.9, venv `.venv` |
| Библиотеки | ultralytics 8.4.184, torch 2.14.1+cpu, opencv-python 5.0.0.93, onnxruntime 1.31.0 (см. `requirements-experiment.txt`) |
| Видео | `data/videos/0_te1.mp4`: 1920×1080, 24.83 fps, 372 кадра (~15 с), стационарная камера над цехом прессов |

## Команды запуска

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-experiment.txt

# веса и видео в git не хранятся — положить вручную:
#   models/yolov8s.pt, data/videos/0_te1.mp4

# 1. детекция + трекинг + бенчмарк
.\.venv\Scripts\python.exe scripts/run_yolo_video.py --model models/yolov8s.pt `
    --source data/videos/0_te1.mp4 --conf 0.25 --imgsz 640 --device auto --out outputs

# 2. экспорт в ONNX (opset 12, 640x640, static, onnxslim)
.\.venv\Scripts\python.exe -c "from ultralytics import YOLO; YOLO('models/yolov8s.pt').export(format='onnx', opset=12, imgsz=640, dynamic=False, simplify=True)"

# 3. проверка ONNX через чистый onnxruntime против PyTorch
.\.venv\Scripts\python.exe scripts/check_onnx.py --onnx models/yolov8s.onnx --pt models/yolov8s.pt `
    --source data/videos/0_te1.mp4 --out outputs/0_te1_onnx_check.json
```

`--device auto` выбирает CUDA → MPS → CPU. `--max-frames N` ограничивает прогон первыми N кадрами.

Артефакты (не в git): `outputs/0_te1_annotated.mp4`, `outputs/0_te1_detections.csv`,
`outputs/0_te1_benchmark.json`, `outputs/0_te1_onnx_check.json`, `models/yolov8s.onnx`.

| Метрика | Значение |
|---|---|
| Кадров обработано | 372 / 372 |
| Preprocess, мс/кадр | 2.13 |
| Inference, мс/кадр | 97.52 |
| Postprocess, мс/кадр | 1.05 |
| FPS модели (pre+inf+post) | 9.93 |
| FPS end-to-end (декод + трекинг + отрисовка + запись) | 7.13 |
| Общее время | 52.2 с |

Видео идёт с 24.8 fps, т.е. на этом CPU обработка в реальном времени **не** достигается (~3.5× медленнее).
Для real-time нужен ускоритель, прореживание кадров (5–8 fps для контроля СИЗ обычно достаточно) или меньший imgsz.

## ONNX-экспорт

- `models/yolov8s.onnx`: opset 12, вход `images [1, 3, 640, 640]` (static), выход `[1, 84, 8400]`, 42.8 МБ,
  упрощён onnxslim 0.1.98 без ошибок, `onnx.checker` проходит.
- Выход головы без NMS: NMS и letterbox надо реализовать на стороне ускорителя/хоста
  (референсная реализация — `scripts/check_onnx.py`, функции `preprocess` / `postprocess`).
- Проверка на 7 кадрах (0, 60, …, 360):

| Проверка | Результат |
|---|---|
| Макс. |Δ| сырого выхода ONNX vs PyTorch на одном тензоре | 0.0019 |
| Детекций PyTorch / ONNX | 48 / 49 |
| Сопоставлено (тот же класс, IoU ≥ 0.5) | 48 из 48 |
| Средний IoU сопоставленных боксов | 0.993 |
| Средняя |Δconf| | 0.009 |
| onnxruntime CPU, inference | ~95 мс/кадр |

Единственная лишняя детекция ONNX — пограничная (conf ≈ 0.25) на кадре 0: ultralytics для `.pt` использует
прямоугольный letterbox 640×384, а статическая ONNX-модель — квадрат 640×640, отсюда мелкие расхождения у порога.

## Наблюдения о качестве

**Люди (person).**
- Люди мелкие: высота бокса 59–236 px на кадре 1080p (медиана ~100 px), после ресайза до 640 — ~35–60 px.
  Уверенность невысокая: медиана conf 0.47, четверть детекций в диапазоне 0.25–0.35.
- Есть явные **пропуски**: рабочий у пресса в левой части цеха (кадр ~250) не детектируется вовсе; люди,
  частично закрытые станками, и сидящий у левого края кадра теряются или классифицируются как `suitcase`.
- Дальний коридор справа: группы из 2–4 человек рядом дают слипшиеся/пересекающиеся боксы.
- **Трекинг**: два стабильных трека на весь ролик (id 1 и 4, conf ~0.7), остальные рвутся — короткие треки по
  1–30 кадров и переприсвоение id (18 id на ~8 человек). Для подсчёта «времени в зоне» нужен более
  стабильный детектор и/или настройка ByteTrack (`track_buffer`, `match_thresh`), либо BoT-SORT с ReID.

**Ложные срабатывания.** Все не-person классы на этом видео — ложные (оборудование, похожее на бытовые
предметы COCO). Для кейса их нужно просто отфильтровать (`classes=[0]`), но это показывает, что домен
«цех» сильно отличается от COCO.

**Мелкие объекты.** imgsz=640 на 1080p — потеря деталей примерно в 3 раза. Каски, жилеты, перчатки на людях
высотой ~40 px после ресайза различить практически невозможно даже специализированной моделью. Варианты:
imgsz 960–1280, тайлинг (SAHI), или двухстадийная схема «person → кроп → классификатор СИЗ».

## Покрытие сценариев кейса

| Сценарий | Покрывается YOLOv8s COCO? |
|---|---|
| Наличие/подсчёт людей в кадре | Частично — работает, но с пропусками у оборудования и рваным трекингом |
| Вход человека в опасную зону (полигон у пресса, проход) | Частично — можно сделать геометрией поверх bbox person + track_id; качество ограничено пропусками |
| Нахождение человека в зоне дольше N секунд / одиночная работа | Частично — нужна стабилизация трекинга |
| Отсутствие каски | **Нет** — класса нет в COCO |
| Отсутствие сигнального жилета / спецодежды | **Нет** |
| Перчатки, очки, СИЗ органов дыхания | **Нет** |
| Падение / лежащий человек | Нет напрямую (только эвристика по соотношению сторон bbox или pose-модель) |
| Курение, телефон в цеху | Нет / ненадёжно (`cell phone` есть в COCO, но объект слишком мелкий) |
| Погрузчик / техника рядом с людьми | Нет — класса «forklift» в COCO нет (`car`/`truck` только как суррогат) |
| Дым, огонь, разлив | **Нет** |
| Перекрытие проходов / эвакуационных выходов | Нет (нет классов для паллет/тары) |

## Выводы и следующие шаги

1. YOLOv8s COCO годится как **детектор людей** и база для зональной логики, но не для СИЗ.
2. Дообучение (fine-tune) на датасете СИЗ: классы person, helmet/no_helmet, vest/no_vest (+ forklift, fire/smoke
   при необходимости). Публичные датасеты: SHWD, Hard Hat Workers, SH17, Construction-PPE; плюс разметка
   кадров с камер заказчика.
3. Для мелких объектов: imgsz 960/1280 или тайлинг; сравнить по скорости на ускорителе LinQ.
4. Фильтр классов `classes=[0]`, порог conf подобрать по разметке (0.25 даёт много слабых детекций).
5. Трекер: подобрать параметры ByteTrack или BoT-SORT+ReID, чтобы id не рвались.
6. ONNX (opset 12, static 640) готов к переносу; на стороне ускорителя нужно реализовать letterbox и NMS.
